# Infrastructure & Release

## Architecture (per environment, DEV and PROD each in their own GCP project)

```
Browser ──HTTPS──▶ Cloud Run "frontend" (nginx: React SPA + reverse proxy for /api)
                        │  /api/*
                        ▼
                   Cloud Run "backend" (Quarkus) ──Cloud SQL connector (IAM + TLS)──▶ Cloud SQL PostgreSQL 17
```

- **One origin**: the browser only talks to the frontend service, which proxies `/api` to the backend. This keeps the
  `SameSite=Strict` session cookie working and avoids CORS. No load balancer needed (saves ~18 €/month per env).
- **Database**: Cloud SQL (PostgreSQL 17, supports the `vector` extension used by the migrations), automated backups,
  public IP *without* authorized networks - reachable only via the Cloud SQL connector. Credentials are generated by
  Terraform and live in Secret Manager (db password, JWT secret).
- **Why not Supabase?** It would be cheaper/free for a start, but it is outside GCP, and you would have to manage
  network access and secrets across two vendors. Because the app only needs plain PostgreSQL, switching later only means
  changing `QUARKUS_DATASOURCE_*`. Staying on Cloud SQL is the simplest consistent setup.
- **Cost (rough)**: DEV ≈ 10 €/month (db-f1-micro, Cloud Run scales to zero), PROD ≈ 35 €/month (db-g1-small, 1 warm
  backend instance).
- **Terraform** (`terraform/`) owns infrastructure; the **pipeline** owns the container image of the Cloud Run services
  (Terraform ignores image changes). Terraform is applied manually (rarely needed); the pipeline deploys with a
  least-privilege service account via Workload Identity Federation (no keys stored in GitHub).

## Release process

| Step         | Trigger                                                       | What happens                                                                                                                                                                                                        |
|--------------|---------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| CI           | Pull request                                                  | backend build + tests, frontend build, Terraform fmt/validate, Liquibase against a throw-away Postgres, Docker builds                                                                                               |
| Deploy DEV   | Merge/push to `main`                                          | CI again → build images (tag = commit SHA) → Liquibase migration → deploy backend → deploy frontend → smoke test                                                                                                    |
| Release PROD | Publish a GitHub Release with tag `vX.Y.Z` on a `main` commit | Gate: tag format, commit on `main`, **successful DEV deployment of the same SHA** → manual approval (GitHub environment) → copy the *same images* from DEV (no rebuild) → Liquibase migration → deploy → smoke test |

Notes:

- Database migrations run **before** the new backend is deployed, so they must be backward compatible (expand/contract:
  add columns first, remove them in a later release).
- Rollback of the apps: `gcloud run services update-traffic <service> --to-revisions=<previous-revision>=100`. Database
  changes are not rolled back automatically.

## One-time manual setup

Prerequisites: `gcloud`, `terraform >= 1.5`, a GCP billing account.

1. **Create two GCP projects** (e.g. `<prefix>-ppmp-dev`, `<prefix>-ppmp-prod`), link billing, and run
   `gcloud auth application-default login` with a user that is Owner of both.
2. **Create a state bucket per project** (versioned, private; the state contains generated secrets):
   ```bash
   for env in dev prod; do
     P=ppmp-$env
     gcloud storage buckets create gs://$P-tfstate --project $P --location europe-west3 --uniform-bucket-level-access
     gcloud storage buckets update gs://$P-tfstate --versioning
   done
   ```
3. **Edit** `terraform/environments/{dev,prod}/terraform.tfvars` and `backend.hcl` (replace `CHANGE-ME-…`).
4. **Apply DEV first, then PROD**:
   ```bash
   cd infrastructure/terraform/environments/dev
   terraform init -backend-config=backend.hcl && terraform apply
   terraform output github_environment_variables
   ```
   (The first apply can fail once on API enablement timing - just run it again.)
5. **GitHub → Settings → Environments**: create `dev` and `prod`. Add the values of the Terraform output
   `github_environment_variables` as *environment variables* (not secrets) of the matching environment. In `prod` also
   add
   `DEV_GCP_PROJECT_ID` (= DEV project id).
    - `prod`: enable **Required reviewers** and restrict deployment to protected branches/tags.
    - `dev`: restrict deployment branches to `main`.
6. **Protect `main`** (Settings → Branches / Rulesets): require pull request, require the CI checks
   (`Backend build & test`, `Frontend lint, build`, `Terraform format & validate`, `Database migrations apply cleanly`),
   no direct pushes. Optionally restrict who can create `v*` tags / releases.
7. Merge to `main` to trigger the first DEV deployment; create a Release `v0.1.0` to deploy to PROD.
8. (Optional) Custom domain: map a domain to the frontend Cloud Run service (Cloud Run → Manage custom domains).

If your organization enforces *Domain restricted sharing*, `allUsers` as Cloud Run invoker is rejected: ask your admin
for an exception on these two projects.
